\section{项目概况}

\subsection{要解决的问题}
本次实验由于甲方同学的特殊需求（主要是指其认为的预约是一种求购意向的表达而非延迟售卖，以及平台托管货款的模式），
所以产品会类似于网易buff（https://buff.163.com/），而非咸鱼（https://www.goofish.com/）。由于这种特殊性，本次实验要解决的问题主要有（按照购买流程排序）：

\begin{itemize}
  \item 商品信息由卖家自行发布，质量与合规性缺少把关，需要管理员审核、下架与违规处理机制；
  \item 同一商品可能有多件库存，多个买家同时预约时容易出现重复预约、超卖与旧页面误操作，需要保证并发安全和数据的一致性；
  \item 交易同时需要买卖双方及时的确认（买家预约、卖家确认、买家付款、卖家发货、买家确认收货），交易需要保证是在双方及时沟通和确认下完成的；
  \item 买卖双方在付款与发货之间存在信任缺口，在交易之间需要平台托管货款，确认收货后再向卖家打款；
  \item 交易达成后仍可能出现不满意或违规交易，需可追溯的沟通记录与退货退款通道；
\end{itemize}

因此，本系统要解决的问题是：在买卖双方之间建立一个规则明确、状态可追踪、并发安全、数据一致性能得到保证的线上二手交易流程，具体见下述项目目标：

\subsection{项目目标}

\begin{enumerate}
  \item 明确的交易规则：明确买家、卖家、管理员三类角色的权限边界。
  \item 覆盖商品从草稿、审核、发布、修改、下架到违规隐藏的完整生命周期。
  \item 科学的运行流程：以“预约—卖家确认—限时付款—平台托管—确认收货—打款”为主线，定义交易流程及其超时、取消与退货分支。
  \item 并发安全和多端数据一致性：对并发预约、重复预约、旧页面操作给出可执行的冲突处理规则与量化验收标准，同时多端数据要尽量快速地保证一致性。
\end{enumerate}

\subsection{系统范围}

本期系统包含以下功能范围：

\begin{itemize}
  \item 用户与权限：买家、卖家自助注册登录；管理员账号由系统预置；角色权限与互斥规则。
  \item 商品管理：草稿箱、提交审核、批准发布、修改重审、下架、违规隐藏、状态与可见性控制。
  \item 商品查询：按关键词、分类、价格区间、状态查询；按匹配度、近期评价、浏览量、销量加权排序。
  \item 交易流程：预约、取消预约、超时自动取消、卖家确认、限时付款、交易完成。
  \item 资金流程：平台托管货款、确认收货后打款、长期未确认自动打款、退货退款。
  \item 沟通与监管：买卖双方消息沟通、消息留存、管理员在举报场景下查看会话。
  \item 非功能约束：前后端分离与敏感数据保护、多端功能与数据一致、并发冲突处理与旧页面失效。
\end{itemize}

\subsection{明确不实现的内容}
\begin{itemize}
  \item 真实支付渠道；真实资金结算；物流平台接口对接；
  \item 买卖双方绕过平台的线下交易（不考虑）。
  \item 商品不设置延迟售卖。预约仅定义为发起购买意向。
\end{itemize}

\subsection{访谈中的困难与解决方法}
（主要是llm生成，经过人工修改确认）
\begin{enumerate}
  \item 口语化与信息分散。受访者的表述包含重复、停顿和跳跃，同一规则可能分散在多个时间点。解决方法是先保留原始转写，再整理润色版，并为每段对话标注行号（如 INT-01-L211），使需求条目可以逐条回溯到原话。
  \item 前后表述不一致。例如“预约后 24 小时内未付款自动取消”与“卖家确认后 2 小时内付款”在计时口径上并不自然衔接；乙方提出的“确认与交易完成是否只属于购买环节”也未在访谈中当场澄清。解决方法是将冲突显式记录为待确认项，经补充沟通后删除前者，统一为“卖家 24 小时内确认、确认后 2 小时内付款”的时间线。
  \item 边界情况缺失。草稿箱容量、草稿保存期限、审核不通过的处理、旧页面失效的判定方式等，访谈中只给出方向性描述。解决方法是先按同一字段结构登记为待确认需求，再逐项补充沟通，避免自行臆造规则。
\end{enumerate}


\subsection{需求整理中的困难与解决方法}
（主要是llm生成，经过人工修改确认）
\begin{itemize}
  \item 非功能需求容易写成“安全”“稳定”“体验良好”，且容易缺失对象、条件和判断标准。解决方法详细分析每条非功能需求中的对象、条件与判断标准三个部分，并给出可执行的数量指标与测试手段。
  \item 初期出现了同一目标被拆成多条需求的情况，例如草稿箱规则、排序权重、旧页面失效实现方式各自单列。解决方法是以“一条需求一个主要目标”为准合并重复条目，删除被吸收的编号，同时保持其余编号不变。
  \item 异常分支写了但验收方法没有覆盖。解决方法是逐条对照“异常或边界情况”补充验收用例，使每个异常都有对应的可执行检查。
\end{itemize}


\subsection{人工审查的作用}

举出chat.txt中的一些典型记录作为例子分析：

\begin{itemize}
  \item REV-000：消息形式与留存要求（由于对应访谈内容有缺失）被标注为待确认状态；经人工审核明确支持文字与图片、记录留存 30 天。
  \item REV-001：REQ-017 缺少可供测试使用的正常结果->审查后补充相应的对象、条件与四条量化判断标准。
  \item REV-002：补充沟通确认“预约即发起购买意向，先预约、卖家确认后付款”，据此删除重复的 REQ-024，并清理关联引用。
\end{itemize}


\subsection{AI 辅助需求整理的作用与局限}
作用：
\begin{enumerate}
  \item 1.结构化：把口语化访谈快速整理为统一字段的需求条目；明确了口语化访谈所带来的模糊性；生成了美观的报告文件的模板以及流程图，以便人工修改(确实生成很好，我修改之处很少)；
  \item 2.一致性检查：发现同一规则在不同条目中的表述冲突，例如具体时间表述在访谈上下文中不一致（例如卖家确认后）等等，而且能快速定位完整，不重不漏（这很好，古法coding时经常会出现改动一处变量名，但是忘记修改其他地方的引用的情况）；
  \item 3.提供合理的建议：为非功能需求生成对象、条件与判断标准，为异常分支生成验收用例。
\end{enumerate}

局限同样明显：

\begin{itemize}
  \item 过度细化：会自行补全访谈中未说明的细节。且这些细节很可能是不必要的。（例如在第一版的报告文件中的“明确不实现的内容”给我整了好多个条目）；
  \item 容易把“合理推测”写成“已确认”，导致状态与内容不一致；需要人工逐条核对来源并更新状态；
\end{itemize}
